Thanos Compactor

In a distributed TSDB system, thousands of small 2-hour data blocks are continuously uploaded to Object Storage by Thanos Sidecars. Without intervention, querying this data becomes impossibly slow due to massive metadata overhead, huge index lookups, and millions of tiny files.

What is the Compactor? The Thanos Compactor applies Prometheus local TSDB compaction logic directly to blocks residing in Object Storage. It is a background maintenance component. It is NOT part of the query path and does NOT serve queries.

🧠 Mental Model

  • Sidecar: Writes 2-hour raw blocks to Object Storage.
  • Store Gateway: Reads blocks from Object Storage for queries.
  • Compactor: Cleans, merges, downsamples, and garbage-collects blocks in Object Storage.

Core Internal Mechanics

1. The Singleton Requirement (CRITICAL)

The Compactor is not concurrency-safe. It must run as the ONLY ONE instance per Object Storage bucket. Running multiple compactors will lead to overlapping compactions, duplicate data, corrupted index files, and broken data consistency. It MUST be deployed with replicas: 1. Two concurrent Compactors can both attempt to compact the same group, both uploading different output blocks and both deleting the source blocks — causing permanent data loss.

2. Block Grouping by External Labels

The Compactor scans Object Storage and groups blocks based on their External Labels (which identify the source Prometheus instance). Blocks from the same Prometheus instance (same label set) that are adjacent in time are merged. Blocks with {cluster="eu-west"} are only ever merged with other {cluster="eu-west"} blocks. Blocks with different labels are never merged together. This ensures data from different clusters/replicas is never incorrectly combined.

Wrong or missing external labels lead to broken compactions!

3. Compaction Ranges (Prometheus TSDB Engine Rules)

Compaction merges blocks by following the Prometheus TSDB compaction range ladder. Each level targets a specific time range:

Level 1: 2h (raw from Sidecar)
Level 2: 6h (compact 3× 2h blocks)
Level 3: 24h (compact 4× 6h blocks)
Level 4: 48h (compact 2× 24h blocks)
Level 5+: 96h → 192h → 336h (14d) (continuing ×2 doubling)

A block qualifies for the next range when enough blocks exist to fill the target window. The planner groups blocks within each range and merges them into a new, larger block. Source blocks are deleted (after --delete-delay).

4. Downsampling

Downsampling is a separate pass run AFTER compaction completes. It does NOT replace raw blocks — it creates additional blocks alongside them.

  • 5m downsampling: created for raw blocks whose minTime is older than 40 hours. The 5m block stores AggrChunk with sub-fields: count, sum, min, max, counter per 5-minute interval.
  • 1h downsampling: created for 5m-downsampled blocks whose minTime is older than 10 days (240 hours). The 1h block is created FROM the 5m block, not from raw.

Crucially: Downsampling is NOT primarily for saving storage. Each downsampled series stores 5 aggregations (count, sum, min, max, counter), so a dataset with 1M series becomes 5M series at 5m resolution. The real benefit is query speed for long time ranges (months/years). Downsampled blocks are stored alongside raw data — they do not replace it. Deleting raw requires configuring --retention.resolution-raw.

5. Retention & Two-Phase Deletion

Retention is applied AFTER compaction and downsampling loops, never before. Retention flags:

  • --retention.resolution-raw=0d — 0d means keep forever (disabled retention)
  • --retention.resolution-5m=0d
  • --retention.resolution-1h=0d

A block is deleted only when its maxTime (not minTime) is older than the retention duration. Deletion is two-phase: first a deletion-mark.json is written inside the block directory, then after --delete-delay (default 48h) the block is physically removed. This gives Store Gateway time to stop serving the block before it disappears.

6. Consistency Delay

--consistency-delay=30m (default): Fresh blocks younger than 30 minutes are ignored by the Compactor. This prevents compacting partially-uploaded blocks from Sidecars. The upload is not instantaneous — a block may appear in the bucket before all its files are fully written. Set this to 0 only if you control all block producers.

Failure Modes & Operational Realities

  • Compactor Down: The system (ingestion & querying) continues working perfectly. However, over time, Object Storage fills with unoptimized small blocks, causing query latency to degrade progressively.
  • Halted Compaction: If the Compactor hits malformed blocks or downsampling errors, it halts to protect data safety (leaving a compaction.err.json). A backlog builds up until the issue is resolved.
  • Out of Memory (OOM): Merging large blocks requires loading massive indexes into memory. Compactor must be provisioned with sufficient RAM and local disk space for the data directory.
  • Anti-pattern — Raw retention too short: If --retention.resolution-raw is set shorter than 40h and downsampling is enabled, raw blocks may be deleted before the 5m downsampled blocks are ever created. You will permanently lose sub-5m resolution data. Always keep raw retention ≥ 40h minimum.

🔗 System Flow

Sidecar → Object Storage → Compactor (Optimizes) → Store Gateway → Query

The Compactor is the ONLY component in Thanos that writes AND deletes data in Object Storage.

Hands-On Scenario Exercises

Use the interactive simulation below to explore each scenario. Follow the steps and observe the behavior in the storage lanes and log panel.

Scenario 1: Basic Compaction

Click "Upload 2h Raw Block" 3 times to add three blocks with cluster=eu-west. Then click "Trigger Compaction Cycle". Watch the three L1 (2h) blocks merge into one L2 (6h) block following the Prometheus range ladder: 2h × 3 → 6h.

Scenario 2: Label-Based Grouping

Upload 3 blocks with "Upload 2h Raw Block" (eu-west) and 1 block with "Upload Block (Different Labels)" (us-east). Run compaction. Notice that the eu-west blocks merge together but the us-east block stays separate — blocks with different labels are never merged.

Scenario 3: Downsampling in Action

Upload several raw blocks. Move the Simulated Time slider past 40 hours. Run compaction. Observe 5m downsampled blocks appearing in Lane 2 — blocks older than 40h get a 5m downsample. Move time past 10 days (240h), run again, and watch 1h blocks appear in Lane 3 (created FROM the 5m blocks, not raw).

Scenario 4: Retention & Two-Phase Deletion

Set --retention.resolution-raw to 7d. Upload blocks and advance simulated time past 7 days. Run compaction. Observe blocks getting deletion-mark.json badges first, then being physically removed after the --delete-delay. Try setting raw retention to 2d with downsampling enabled — notice the anti-pattern warning.

Scenario 5: Singleton Violation

Click "Simulate Multiple Compactors". Observe the fatal error — the Compactor halts immediately because it detects another instance against the same bucket. This demonstrates why Compactor MUST be deployed with replicas: 1. Click "Reset Storage Bucket" to recover.

Scenario 6: Replica Blocks & Separate Groups

Upload blocks with "Upload 2h Raw Block" (replica=0) and then "Upload Replica Block" (replica=1). These blocks have the same cluster label but different replica labels, forming separate compaction groups. Run compaction and observe they are grouped and processed independently.
