Module: Compactor

Thanos Compactor

In a distributed TSDB system, thousands of small data blocks are continuously uploaded to Object Storage by Thanos Sidecars. Without intervention, querying this data becomes impossibly slow due to massive metadata overhead, huge index lookups, and millions of tiny files.

What is the Compactor? The Thanos Compactor applies Prometheus local TSDB compaction logic directly to blocks residing in Object Storage. It is a background maintenance component. It is NOT part of the query path and does NOT serve queries.

🧠 Mental Model

  • Sidecar: Writes blocks to Object Storage.
  • Store Gateway: Reads blocks from Object Storage.
  • Compactor: Cleans, merges, and optimizes blocks in Object Storage.

Core Internal Mechanics

1. The Singleton Requirement (CRITICAL)

The Compactor is not concurrency-safe. It must run as the ONLY ONE instance per Object Storage bucket. Running multiple compactors will lead to overlapping compactions, duplicate data, corrupted index files, and broken data consistency.

2. Block Grouping & Merging

The Compactor scans Object Storage and groups blocks based on their External Labels (which identify the source Prometheus instance). Blocks from the same Prometheus instance (same labels) that are adjacent in time are merged from smaller blocks (e.g., 2h) into larger, highly optimized blocks (e.g., 8h, 2d, 14d). Wrong or missing external labels lead to broken compactions!

3. Downsampling

Downsampling creates lower-resolution aggregations of old data (5m and 1h intervals). Crucially: Downsampling is NOT primarily for saving storage. It exists for faster long-range queries. Querying 1 year of raw data requires scanning huge amounts of data. Querying downsampled data is fast. Downsampled blocks are stored alongside raw data, they do not replace it.

4. Retention & Deletion

The Compactor is the only component in Thanos that deletes data. It enforces configured retention policies (e.g., delete raw data after 30 days) and physically removes the blocks from Object Storage.

Failure Modes & Operational Realities

  • Compactor Down: The system (ingestion & querying) continues working perfectly. However, over time, Object Storage fills with unoptimized small blocks, causing query latency to degrade.
  • Halted Compaction: If the Compactor hits malformed blocks or downsampling errors, it halts to protect data safety (leaving a compaction.err.json). A backlog builds up.
  • Out of Memory (OOM): Merging large blocks requires loading massive indexes into memory. Compactor must be provisioned with sufficient RAM and local disk space.

🔗 System Flow

Sidecar → Object Storage → Compactor (Optimizes) → Store Gateway → Query
