Start here

Think of Querier as the traffic controller for PromQL in a Thanos cluster.

Grafana or another client sends one Prometheus-style query to Querier. Querier decides which backends must be contacted, asks them for the needed series through StoreAPI, optionally deduplicates HA replicas, evaluates the PromQL expression, and then returns the final answer.

The request path

What Querier does not do

  • It does not scrape targets.
  • It does not store TSDB blocks itself.
  • It does not compact or downsample blocks.
  • It does not replace PromQL with a custom language.
  • It asks backends for data and then evaluates PromQL on what comes back.

What to expect

Accuracy boundary

This lab models the common Query path from official Thanos Query docs: QueryAPI request, discovered StoreAPI endpoints, concurrent selector fanout, optional dedup by replica labels, partial-response behavior, and source-resolution choice. It does not simulate distributed execution mode, Query Frontend caching, or the internal sample-by-sample differences between the penalty and chain deduplication functions.

Wrap Up

Use this summary after you finish the scenarios.

One HTTP query in

Querier exposes the Prometheus-compatible HTTP API. Clients do not talk to StoreAPI directly.

Many StoreAPI requests out

Querier discovers relevant stores and fans out selector requests concurrently to gather the needed series.

One evaluated answer back

After gathering data, Querier evaluates PromQL and returns results, optionally with warnings if partial responses are allowed.
