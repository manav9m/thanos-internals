Thanos Store Gateway

While the Thanos Sidecar handles real-time queries for recent data on local disk, long-term durable metrics reside in Object Storage (e.g., AWS S3, GCS). Querying full TSDB blocks directly from Object Storage is slow and massively inefficient.

What problem does the Store Gateway solve? It acts as an API layer over object storage, not a database itself. It implements the gRPC StoreAPI (the exact same API as the Sidecar), allowing Thanos Query to seamlessly read historical data without downloading the entire database.

Core Behavior & Mental Model

  • Object Storage: Holds the raw, massive historical data.
  • Store Gateway: The "smart reader." It does not download full data. It fetches only the exact bytes required to answer a specific query.
  • Query: The orchestrator. It does not differentiate between Sidecar (recent) and Store (historical).

Startup Sync Behavior

When the Store Gateway starts, it must build a local understanding of what exists in remote storage:

  1. Scans the object storage bucket for TSDB blocks.
  2. Downloads the meta.json (labels, time bounds) and index headers (a small subset of the block's index) to local disk.
  3. Uses minimal local disk space (a few MB per block) to "advertise" available data to Queriers.

Periodically, it re-scans the bucket to detect new blocks uploaded by Sidecars or old blocks deleted by Compactors.

Internal Data Flow (The Query Path)

This is the critical path for reading historical data:

Query → Store Gateway → Metadata Filter → Index Lookup → Chunk Fetch
  1. Step 1: Metadata Filter: Store looks at local `meta.json` to identify which blocks match the query's time range.
  2. Step 2: Index Lookup: It uses the local index headers (and Index Cache) to find exactly where matching series live inside the remote block.
  3. Step 3: Chunk Fetch: If data isn't in the Chunk Cache, Store performs highly optimized HTTP Range Requests to Object Storage to fetch only the required chunk bytes.

Caching Layers

To reduce latency and costly egress from Object Storage, Store Gateway employs caching:

  • Index Cache: Caches Postings and Series lookups.
  • Chunk Cache: Caches actual sample data fetched from remote chunks.

Failure Modes & Operational Realities

  • ❌ Myth: Store Gateway downloads all data. (Reality: It only fetches specific bytes during queries).
  • ❌ Myth: It acts as local long-term storage. (Reality: It has no data of its own, local disk can be deleted and rebuilt).
  • Store Gateway Down: Historical data is unavailable, but recent data via Sidecar still works.
  • Object Storage Slow: Direct impact on query latency for historical queries.
