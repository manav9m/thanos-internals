Module: Store Gateway

Thanos Store Gateway

The Thanos Store Gateway implements the Store API on top of historical data in an object storage bucket. It acts primarily as an API gateway, providing Queriers with access to long-term storage without requiring vast amounts of local disk space.

Deep Internal Working

When an incoming query requests historical data, the Store Gateway executes the following flow:

  1. Index Header Lookup: On startup, Store downloads tiny pieces of each block's index (the `index-header`) to local disk. It maps the query labels to find which blocks contain the data.
  2. Index Cache: It checks the Index Cache (In-Memory, Memcached, or Redis) for Postings and Series metadata to quickly pinpoint the exact byte offsets inside the remote block.
  3. Chunk Cache: It checks the Caching Bucket for the raw sample data (Chunks).
  4. Byte-Range Request: If the chunk is not cached, Store issues a highly optimized HTTP byte-range request to Object Storage, fetching only the needed bytes (not the whole block!).

Guided Examples

Example 1: The First Query (Cache Miss)

Goal: See how Store Gateway fetches data from Object Storage.

  1. Click "Query Historical Block".
  2. Observation: The caches will flash red (miss). The Store Gateway calculates offsets and sends a byte-range request to Object Storage.

Example 2: Repeated Queries (Cache Hit)

Goal: Observe caching performance.

  1. Click "Query Historical Block" again for the same block.
  2. Observation: The caches flash green (hit). No request is sent to Object Storage, resulting in much faster query times and lower egress costs.

Example 3: Time-Based Partitioning

Goal: See how Store nodes can be sharded.

  1. Toggle the --min-time and --max-time flag.
  2. Attempt to query a block outside the configured time range.
  3. Observation: The Store Gateway simply ignores the query, allowing you to run multiple Store nodes handling different time periods.

Failure Modes

  • OOM (Out of Memory): High cardinality queries can cause Store Gateway to load massive amounts of series/postings into memory. Proper index-cache sizing is critical.
  • High Latency: If caches are too small or disabled, Store makes constant requests to Object Storage. Object Storage latency translates directly to query latency.
  • Corrupt Index Header: If local index-headers are corrupted or disk is lost, Store must re-download them on startup, delaying readiness.
