Module: Retention & Deletion

Thanos Data Retention

By default, Thanos object storage has NO retention limits. Data is kept forever.

Retention limits must be explicitly configured on the Compactor to clean up old blocks and save costs.

Resolution-Based Retention

Retention is applied based on the resolution of the block (Raw, 5m, or 1h). This allows you to keep downsampled data for long-term queries while deleting large, raw blocks to save space.

  • --retention.resolution-raw
  • --retention.resolution-5m
  • --retention.resolution-1h

The Deletion Process (Eventual Consistency)

Thanos does not delete blocks immediately. Because readers (Queriers, Store Gateways) might be actively accessing a block, deleting it straight away would cause query errors.

Instead, Thanos uses a two-step deletion process:

  1. Mark for Deletion: The Compactor uploads a deletion-mark.json file to the block's directory. This signals to readers to stop using the block.
  2. Delayed Deletion: The Compactor waits for a duration defined by --delete-delay (default 48h) before finally removing the files from object storage.

Example: The Deletion Lifecycle

Goal: Observe how a block ages out of retention and is safely deleted.

  1. Set Raw Retention to 14d and Delete Delay to 2d.
  2. Click "Advance Time (1 Day)" repeatedly.
  3. When the raw block reaches 14 days old, observe a red X appear. This is the deletion-mark.json being added.
  4. Advance time 2 more days. The block will be fully deleted from storage.

Common Pitfalls

  • Retention before Downsampling: If your retention for a resolution is shorter than the time needed to downsample it (e.g., raw retention < 40h), the data will be deleted before it can be downsampled!
  • Halted Compactor: Retention is applied after compaction and downsampling loops. If the compactor is halted due to an error (e.g., overlapping blocks), data will never be deleted.
