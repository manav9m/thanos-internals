Module: TSDB Internals

Prometheus/Thanos TSDB

Thanos is built directly on top of the Prometheus Time Series Database (TSDB). Understanding how data flows from memory to disk is crucial for operating Thanos.

Deep Internal Working

The TSDB uses a multi-stage approach to balance high ingestion throughput with efficient querying:

  • Head Block (Memory): Active incoming samples are kept in memory in "chunks". A chunk holds data for a single time series. Typically, chunks hold up to 120 samples.
  • Write-Ahead Log (WAL): Because the Head is in memory, a crash would cause data loss. Every sample appended to the Head is simultaneously written to an append-only file on disk called the WAL.
  • Memory-Mapping (mmap): When a chunk in the Head block gets full, it is flushed to disk and memory-mapped. This keeps memory usage stable while keeping recent data available for fast querying.
  • Persistent Blocks: Periodically (default 2h), the active Head block is "cut". The mapped chunks and the current WAL are compacted into a persistent, immutable Block directory (containing an index, chunks/, and meta.json). The old WAL is truncated.

Guided Examples

Example 1: Ingestion & WAL

Goal: See how data is secured before being persisted to a block.

  1. Click "Simulate Scrape (Ingest Samples)" several times.
  2. Observation: Active chunks in memory fill up. Simultaneously, WAL records are appended to disk ensuring durability against crashes.

Example 2: Chunk Flushing (mmap)

Goal: Understand how TSDB manages memory.

  1. Continue clicking "Simulate Scrape" until memory chunks reach 100% full.
  2. Observation: Full chunks are flushed from RAM to the "mmap" region on disk. They are still readable via memory-mapping, but RAM is freed up for new incoming samples.

Example 3: Block Cutting & WAL Truncation

Goal: See how immutable blocks are created.

  1. Click "Cut Block (2h elapsed)".
  2. Observation: All mmap'd chunks and current Head data are written into a final, immutable 2h Block. The WAL is truncated (cleared), starting fresh for the new Head block.

Example 4: Crash Recovery

Goal: See the WAL in action during an outage.

  1. Ingest some samples so the WAL has records. Do not cut a block.
  2. Click "Simulate Process Crash". The Head and mmap memory are lost.
  3. Click "Start TSDB (Recover)".
  4. Observation: The TSDB replays the WAL from disk to rebuild the exact state of the in-memory Head block before the crash.

Failure Modes

  • WAL Corruption: If the WAL file is corrupted (e.g., hardware failure, bad disk flush), the TSDB might fail to start. Sometimes requires manual WAL truncation (losing recent un-compacted data).
  • OOM on Startup: Replaying a massive WAL during crash recovery requires high memory spikes. If limits are too tight, the container will OOM loop.
