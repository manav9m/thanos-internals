Prometheus TSDB Architecture

What is TSDB? Prometheus uses a highly optimized Time-Series Database (TSDB) to store metrics. Before understanding Thanos, you must understand exactly how Prometheus stores data locally, because Thanos is designed to integrate directly with this exact storage format.

Goal of this lab: By the end, you will understand how incoming metrics flow from memory into the Write-Ahead Log (WAL), are held in the Head Block, and are eventually compacted into immutable, persistent TSDB Blocks on disk.

1. Write-Ahead Log (WAL) & Crash Recovery

Every scraped sample is immediately written to an append-only file on disk called the Write-Ahead Log (WAL). The WAL is not queried during normal operations; it exists purely as a safety net. If Prometheus crashes, the in-memory data is lost. Upon restart, Prometheus replays the WAL to perfectly reconstruct the lost memory state.

2. The Head Block (Recent Data)

Active, incoming data lives in the Head Block. This block is partially in RAM (for extremely fast writes and reads of recent data) and partially flushed to disk (memory-mapped chunks) as it fills up. When you query Prometheus for "live" data, it queries the Head Block. Thanos Sidecar also reads the Head Block to serve recent data to Thanos Query.

3. Block Creation & Local Compaction

Every ~2 hours, the current Head Block is "cut". The data is compacted and flushed to disk as a new, immutable Persistent Block. Once created, a block is never modified. At this point, the old WAL is truncated (deleted) because the data is now safely stored in the block.

Note: Prometheus performs its own local compaction (merging small 2h blocks into larger ones) entirely independently of Thanos. The Thanos Compactor operates only on blocks after they are uploaded to Object Storage.

4. Internal Block Structure

A TSDB Block is a directory with a specific, globally unique name called a ULID (Universally Unique Lexicographically Sortable Identifier). The ULID ensures blocks can be ordered chronologically. Inside the directory:

  • chunks/: The actual compressed time-series data.
  • index: A highly optimized reverse-index mapping metric labels to chunks, enabling fast query lookups.
  • meta.json: Metadata including the block's minTime, maxTime, and source labels.

Mental Model

  • WAL: The durability safety net. Append-only.
  • Head Block: The "Live" data area. Fast reads/writes.
  • Blocks: Immutable, compressed, long-term storage units (2h spans).

Hands-On Scenario Exercises

Scenario 1: Ingestion & Safety

Click "Simulate Scrape". Observe how data enters the Head Block (RAM) while simultaneously being appended to the WAL (Disk). The data is available for queries in the Head, but safely backed up in the WAL.

Scenario 2: Creating Immutable Blocks

Scrape data until you have several chunks. Click "Cut Block (2h elapsed)". Observe the Head Block being flushed into a permanent Block directory with a ULID, chunks, index, and meta.json. The WAL is then truncated.

Scenario 3: Crash & Recovery

Ingest data (do not cut a block). Click "Simulate Process Crash". The Head Block (memory) is wiped out. Now click "Start TSDB (Recover)". Watch how Prometheus reads the WAL from disk to perfectly rebuild the Head Block.

Connection to Thanos

Now that you understand how Prometheus creates immutable TSDB Blocks every 2 hours... The Thanos Sidecar watches this local TSDB directory. Every time a new block appears, the Sidecar uploads it to Object Storage. This is the foundation of Thanos!
